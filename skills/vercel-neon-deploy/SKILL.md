# Vercel + Neon 网页工具部署

用中文陪用户把本地能运行的网页工具变成可访问的 HTTPS 网站。默认使用网页控制台引导，给出本项目的具体填写值；有合适连接工具且用户要求代操作时才直接操作。不要因采用固定平台而强制改成 Next.js。

## 开始时

先读取当前项目的协作规则、Git 状态、部署文档、依赖和锁文件、构建脚本、入口、路由、数据库实现及环境变量声明。不要读取或输出真实 `.env` 内容。优先沿用有效配置，保护其他人的未提交改动。

能从项目确认的内容不再询问。缺少访问路径时，问用户本地目录或 GitHub 仓库链接；再按依赖顺序只问当前必要的问题，例如“是否需要跨设备保存数据”“使用哪个已有云项目”。非敏感回答可在聊天收集，密码和连接串让用户直接填控制台，不让用户粘贴到聊天。

首次输出：项目类型、是否需要 Neon、需要修改的最小范围、当前进度；随即给出当前步骤的网页链接和字段表。只给眼前可以执行的步骤，用户回报后继续，不一次丢出整份云部署教程。用户仅要方案时提供完整方案，不创建资源或发布。

## 1. 判断是否能部署

- 静态 HTML 或构建型前端：使用 Vercel 静态托管，纯浏览器本地数据可继续用 localStorage，不需要 Neon。
- 原生支持 Vercel 的全栈框架：保留框架识别和默认输出，不套用 `Other` 或 `public`。
- 普通 Node 服务：检查当前平台对框架和运行时的支持，必要时把 HTTP 处理器适配为 Functions；不要把常驻 `listen` 启动命令当成通用构建命令。
- SQLite、JSON 文件、上传文件或进程内状态需要跨实例持久化时：Functions 本地文件不能作为持久化来源。数据库状态迁至 Neon；上传二进制文件另选对象存储，不能假装 Neon 会自动保存文件。
- 长驻进程、长任务、WebSocket 服务端、系统依赖等无法适配时，明确阻碍与最小改造，询问是否改造或另选平台。不要承诺所有本地工具均能直接部署。

只在确需共享持久化时添加 Neon，不凭空添加登录、邀请码或 AI 功能。现有 SQLite/MySQL 不能只换连接串：需检查 SQL、驱动、迁移和数据导入。

免费方案的用途限制、额度、运行时、地区及控制台字段可能变化。每次执行查阅 [Vercel Hobby](https://vercel.com/docs/plans/hobby)、[Neon plans](https://neon.com/docs/introduction/plans) 和相关官方文档；注明核对日期，不写死长期免费承诺。Hobby 的个人非商业限制须核对，商业用途不承诺适用。模型 API、域名及其他服务单独计费。免费方案不满足时说明冲突，不自行升级或绑卡。

## 2. 准备 GitHub 与适配

确认要部署的仓库、分支、子目录以及本地提交是否已推送。没有远程仓库时提供 [GitHub 新建仓库](https://github.com/new) 的字段指导。不要强制公开仓库，不执行 force push；仅有“指导”请求时不代推送。用户已授权发布时可完成必要推送，不重复索要许可。

依据实际项目生成字段，格式参考 [字段与控制台指南](references/console-fields.md)。使用实际包管理器和锁文件，区分安装、测试、构建和输出目录。核对框架运行时与依赖支持版本，不复制来源项目的 Node 版本或函数超时。

需要适配代码时，先做最小改动，补充针对性测试并遵守仓库测试及提交规则，再准备云端配置。不把密钥、连接串、数据库导出或 `.env` 纳入提交，也不把未知的现有配置覆盖成通用模板。

## 3. 按需创建 Neon 和初始化

打开 [Neon 控制台](https://console.neon.tech/)，指导创建 Free 项目或选择现有项目。名称按应用填写，地区尽量接近实际 Vercel 函数地区；确认 branch、database、role 与目标环境。

从 Connect 获取适合当前驱动的连接方式。普通 PostgreSQL 服务端连接通常使用 pooled 主机；保留控制台的 TLS 参数，不通过关闭证书验证修复错误。迁移工具是否需要 direct 连接由其官方文档决定，不把 `DIRECT_URL` 当成所有项目必填项。参考 [连接说明](https://neon.com/docs/connect/connect-from-any-app) 与 [连接池](https://neon.com/docs/connect/connection-pooling)。

按仓库已有迁移工具提供准确命令，或提供待执行 SQL 文件及 SQL Editor 的进入路径。没有迁移脚本时先依据真实数据模型创建，不捏造表名。新数据库可执行初始化；现有数据先备份并检查迁移影响，破坏性操作另获授权。迁移不要在每次请求时执行；是否在发布流程运行依项目设计判断，确保不会让多个 Preview 同时迁移生产库。

已有本地真实数据必须规划导入、核对及切换，不能只创建空表就称迁移完成。Preview 若启用，使用独立数据库或 Neon 分支，并检查当前免费额度；不默认连接生产数据。

## 4. 配置 Vercel 与环境变量

打开 [Vercel 导入项目](https://vercel.com/new)，填写 GitHub 仓库、项目名称、Framework Preset、Root Directory、Build Command、Output Directory、Install Command、受支持的运行时。按项目证据逐行说明“填什么、来源、是否保留默认”。框架管理的字段不要随意覆盖。官方 [构建配置](https://vercel.com/docs/builds/configure-a-build) 可用于核对。

根据代码实际读取的变量生成“变量名｜填写值或取得位置｜环境｜是否敏感｜必填原因”表。只能展示非敏感值或占位说明。数据库连接串、签名密钥和第三方 API Key 只放服务端；`NEXT_PUBLIC_`、`VITE_` 等公开变量会进入浏览器，不得放密码。不要用占位密钥进行真实发布。

生产地址从项目的 Domains 确认，不能假设项目名称一定对应可用域名。需要 `APP_ORIGIN`、OAuth 回调或允许来源时，填写最终 HTTPS 地址和项目所需路径，不能套用聊天中的示例域名。若必须先有部署才能拿地址，先完成受保护的初始化部署，再配置准确地址并重新部署，未验收前不称上线成功。

变量范围明确选择 Production；Preview/Development 只在需要时配置，Preview 密钥和数据隔离。手动配置 Neon 或使用 [Neon Marketplace 集成](https://vercel.com/marketplace/neon) 选其一；集成注入的变量名需与代码匹配，不能再建一套不明来源的库。变量修改后触发新部署，旧部署不会自动使用新值。参考 [环境变量](https://vercel.com/docs/environment-variables)。

## 5. 发布、验收、交接

用户请求实际部署即覆盖必要的常规发布操作；用户选择手动模式时引导其点击 Deploy，不因“到了发布阶段”重复询问。登录、账号授权和敏感字段由用户完成。只有当前请求确实授权时才创建云资源或发布。

先检查构建日志，再在实际生产 URL 验证首页、静态资源、直接访问深层路由、核心 API、认证与跨域，以及一条完整业务操作。仅项目已有健康检查时使用它，不假定所有工具都有 `/healthz`。AI 或其他计费调用说明消耗，避免自动重复测试。涉及持久化时验证刷新、另一会话和重新部署后仍可读到数据；没有完成的检查明确标为待验证。

交付实际网址、仓库分支与提交、部署版本、非敏感字段记录、数据库目标的非敏感标识、已测与待测项、更新和回退方法。不要输出包含凭据的完整连接地址。回退代码不能回退数据库迁移或恢复数据，二者分别处理。

只完成配置/本地测试时说“已准备好，待云端操作”，用户口述部署成功时标注“用户反馈”，不能捏造已发布或已验收。失败时按 [排错指南](references/console-fields.md#排错顺序) 定位；同一问题经两次有依据的调整仍无进展，停止重复发布，报告脱敏证据和下一步，不靠删库、重置数据或付费升级碰运气。
